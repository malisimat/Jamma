# Jamma self-validation

Use this skill from the active Jamma checkout on Windows. Verify its root with `git rev-parse --show-toplevel`, `Jamma.sln` and `AGENTS.md`; locate every script relative to this `SKILL.md`, never from another checkout. Read `doc/diagnostics.md`. Create the successful JSON build record with `scripts/build-validation-record.ps1`, passing distinct paths for `-BuildRecord` and `-BuildLog`; the record path must contain JSON and the log path must contain MSBuild text. Then run `scripts/resolve-jamma-build.ps1` to check `Jamma/bin/x64/<Configuration>/Jamma.exe`, task-file hash and binary hash. No script contains a user-specific path. Never use Start menu, PATH, an installed copy or the main checkout for worktree validation.

Before launch, inspect all Jamma processes and stop the runtime check if another instance may hold unsaved work. Use `scripts/launch-test-session.ps1` only with the validated record and a fresh disposable `defaults.json` path in the ignored run directory. It sets `JAMMA_DEFAULTS_PATH` only for that process and returns PID, path and start time. Confirm the running process executable path matches the exact build before interacting.

On this host, official Computer Use screenshots are unavailable: `getScreenshot()` / `get_window_state(...include_screenshot...)` repeatedly fail with `FrameArrived` or `window capture timed out`. Do not retry, reset, or use screenshot IDs for Jamma validation, and do not alter Windows privacy/security settings or patch the global plugin. The blue target border is only target selection; it does not prove a rendered frame or input delivery.

Computer Use window discovery, accessibility state, keyboard input, and direct window-relative mouse clicks do work. Bind the exact returned Jamma window from the current `listApps()` result. For mouse input, use `app.click([x, y])` with coordinates relative to that returned window and no screenshot ID. Coordinates must come from a known Jamma layout/configuration or a deterministic prior measurement; do not guess from a missing screenshot. Do not use `app.click(elementIndex)` for mouse verification: it depends on unavailable geometry and has either failed or returned without changing state. Direct coordinate click is proven; drag and scroll are not proven on this host and remain unperformed unless a separate canary establishes them.

After each direct coordinate action, verify the result through the Win32 screenshot route below and, where available, refreshed accessibility state or `run.log`. Record `input_method=computer-use-direct-coordinate`; an input call returning is not sufficient evidence by itself.

Before launch, check the Python environment used by the screenshot helper with `python -c "import win32gui, win32process, win32ui, win32con; print('pywin32=available')"`. If that check fails, stop visual validation and report it; do not install packages or invent another capture mechanism. Run `scripts/capture-window-fallback.py` with the validated session PID and a fresh output path. It enumerates visible windows, requires exactly one visible `Jamma` window owned by that PID, captures only that window through the standard Win32 `PrintWindow` API (with a bounded `BitBlt` fallback), and writes a PNG without user-specific paths. Inspect the resulting image directly; reject black, inverted, clipped or stale output. Then pass that PNG through `capture-window.ps1` and `inspect-runtime.ps1`. Record `capture_method=win32-printwindow-fallback` and the original official capture error in the run report. This is the supported visual route for this machine.

Use keyboard input only after binding the exact returned window, then verify its effect through accessibility state, the fallback screenshot, or logs. A screenshot proves one frame only; report process, log, screenshot, input method and interaction evidence separately.

Use `collect-logs.ps1` with the session start time and explicit defaults path to collect timestamp-bounded startup and worker-failure logs. `inspect-runtime.ps1` checks the saved evidence manifests and hashes; the agent must still inspect behavior and log content. Record successes and concrete failures. Close only the disposable Jamma session you launched, without disturbing another process. Prefer keyboard-only orderly close when the app accepts it; if close is unavailable, recheck that the PID still maps to the exact validated binary and terminate only that disposable PID, recording orderly shutdown as unverified. If the Win32 preflight or capture is unavailable, say so; do not substitute an older binary or a desktop-wide screenshot. Real ASIO, MIDI/serial hardware, plugin sound, timing and subjective UX remain manual gates when no reliable probe exists. Do not disturb a live performance or add callback logging.

For cross-thread/audio changes, invoke the checkout's `jamma-review` with its real-time and cross-thread checklist; for texture work use `tga-icon-gen`. Resolve repo-local skills from this checkout.
