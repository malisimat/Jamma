## System understanding

The intended timing flow has four ownership domains:

1. `NinjamConnection::Pump` runs from Scene's job loop. It calls NJClient `Run()`, builds a remote snapshot, and the job thread passes timing through `NinjamTimingCoordinator` while holding `Scene::_sceneMutex` (`Scene.cpp:1382`–`:1396`).
2. The audio callback is the sole writer of live block anchors and the active local follow/map state. `AudioHost::_OnAudio` consumes one coherent timing command before station advancement (`AudioHost.cpp:148`–`:165`), owns `_activeNinjamFollowPolicy`/`_syncPhaseMap` (`AudioHost.h:141`–`:145`), publishes a latest timing observation (`AudioHost.cpp:437`–`:453`), and restores every local station from its immutable audio snapshot (`AudioHost.cpp:456`–`:459`).
3. Job/UI code serializes timing-coordinator calls and timing-command publication through `Scene::_sceneMutex`: the job path at `Scene.cpp:1387`–`:1396`, prompt decisions at `Scene.cpp:394`–`:400`, and connect/disconnect invalidations at `Scene.cpp:254`–`:305`. The audio callback consumes the command mailbox without that mutex.
4. Per-station and per-take audio membership is published as immutable `shared_ptr` snapshots. Scene publishes `_audioStations` with release and AudioHost loads with acquire (`AudioHost.cpp:108`–`:110`, `:156`–`:158`); Station and LoopTake similarly load published audio snapshots before timing fan-out (`Station.cpp:729`–`:804`, `LoopTake.cpp:566`–`:679`). Phase-map geometry in AudioHost and each LoopTake is deliberately audio-thread-only.

The core fixed-size atomic mailboxes are internally race-free under their stated producer constraints. The observation mailbox uses one audio writer, atomic fields, an odd/even sequence, and acquire/release validation (`NinjamTimingObservationMailbox.h:16`–`:67`); its concurrent complete-or-deferred behavior is exercised at `test/JammaLib_Tests/src/ninjam/NinjamTimingObservationMailbox_Tests.cpp:69`–`:109`. The command and local-offset mailboxes use the same bounded coherent-snapshot pattern (`NinjamAudioTimingCommand.h:53`–`:144`, `:147`–`:191`). AudioHost's applied-command receipt is another atomic odd/even snapshot from audio to job (`AudioHost.cpp:113`–`:133`, `:321`–`:329`). Individual Timer fields are atomic, preventing C++ data races, but they do not constitute a coherent multi-field transport snapshot; this distinction is material below.

## Candidate findings

### S07-01 — Remove non-`AudioProc` NJClient access from the audio thread

- **Stage / reviewer:** Stage 7 — thread safety.
- **Scope reviewed / exclusions:** NJClient caller contract and cross-thread access only. Per-call cost/blocking is Stage 8; upstream NJClient implementation is read-only and must not be edited.
- **Severity:** merge blocker.
- **Evidence:** The job thread executes NJClient `Run()` in `JammaLib/src/ninjam/NinjamConnection.cpp:299`–`:404` and reads remote timing for snapshots at `:922`–`:945`. Every audio block, `JammaLib/src/audio/AudioHost.cpp:437`–`:453` calls through `NinjamController::GetLiveTiming`/`NinjamSession::GetLiveTiming` to `NinjamConnection::GetLiveTiming`, which directly invokes `_client->GetPosition`, `GetSampleRate`, `GetActualBPM`, and `GetBPI` at `JammaLib/src/ninjam/NinjamConnection.cpp:709`–`:724` without `_connectionMutex` or an immutable publication. The bundled upstream contract says `Run()` belongs on the main/UI thread and “AudioProc, (and only AudioProc)” belongs on the audio thread at `lib/njclient/njclient.h:165`–`:172`. The disabled export-latency branch would also call `GetPosition` on the audio thread at `NinjamConnection.cpp:573`–`:590` (`ExportLatencyCompensationEnabled` is currently false at `NinjamConnection.h:64`). History places the live getter in `c4c0607`/`d0d208e` and the callback observation in `f36bfe7`, refined by `d6fdb88`.
- **Why it matters:** Connection lifetime is pinned, but NJClient's mutable timing state is neither published nor protected. The audio callback violates the upstream thread-affinity contract and can race `Run()`/snapshot reads or assemble interval, rate, BPM, and BPI from different upstream states. Adding `_connectionMutex` around it would put a blocking lock on the audio callback and violate repository real-time rules.
- **Recommended disposition:** correct. Keep NJClient getters on the permitted job/network owner, assemble one complete immutable remote observation there, and publish it through a fixed-size lock-free/latest-wins handoff. Preserve a separately captured audio-block device/Timer anchor at the audio boundary; reconcile those two clocks without calling upstream getters from the callback. Do not edit NJClient. Keep the dormant compensation path disabled until it obtains timing without forbidden audio-thread getters.
- **Protected timing concepts affected:** remote observation, remote interval/phase, source sample rate, device-audio observation anchor, local Timer anchor. Publication must not collapse these domains.
- **Verification:** add a call-site audit proving `AudioProc` is the only NJClient method reachable from the audio callback; a concurrent observation test that alternates sentinel timing generations and never returns mixed fields; integration coverage for late job observations projected to an audio-block anchor; ThreadSanitizer or equivalent race harness where practical; normal join/reconnect/disconnect tests.
- **Human decision:** pending.

### S07-02 — Remove Scene/network/quantiser mutation from the audio-thread empty-reset path

- **Stage / reviewer:** Stage 7 — thread safety.
- **Scope reviewed / exclusions:** the changed remote-timing dependency reached from the pre-existing empty-scene audio reset. Reset behavior correctness belongs to Stages 9/10; callback cost belongs to Stage 8.
- **Severity:** must fix before merge.
- **Evidence:** `Scene::OnTick` is the audio callback (`Scene.cpp:1582`–`:1589`). When the published station snapshot contains no takes it calls `_ClearTimingState(false)` at `Scene.cpp:1359`–`:1378`. `_ClearTimingState` reads `_networkService->HasConnectedTiming()` and passes raw Scene `_stations` to `SetMidiGrain` at `Scene.cpp:2271`–`:2275`. The connected flag is plain `NinjamTimingTracker::_connected` (`NinjamTimingTracker.h:48`, `:55`–`:65`) written by job/UI coordinator connect/disconnect (`NinjamTimingTracker.cpp:5`–`:26`) under `_sceneMutex`, which the audio path does not hold. `Quantiser::Clear` also resets non-atomic `_masterLoop` and clears `_preReclockTakeIds` at `Quantiser.cpp:132`–`:153`; `SetMidiGrain` iterates the raw mutable Scene station/take containers and publishes remote MIDI-grid state at `Quantiser.cpp:203`–`:247`. Scene's approved cross-thread container is instead the immutable snapshot loaded at `Scene.cpp:1359`–`:1362`. Blame shows the connected-timing dependency entered in `f36bfe7`, while remote MIDI-grid clearing at `Quantiser.cpp:217`–`:218` was added in `e72f3b0`.
- **Why it matters:** There is a direct C++ data race on `_connected`. The same callback also mutates job/UI-owned Quantiser objects and traverses `_stations` concurrently with remote-station membership changes, bypassing the immutable snapshot pattern. It can become a second writer to each take's remote-grid sequence while the job thread publishes accepted remote geometry.
- **Recommended disposition:** move the empty/reset decision to the Scene/job owner, or publish one immutable reset command/state into the existing audio-boundary model. Audio code should use its station snapshot only and mutate audio-owned Timer/take state at the boundary; job/UI code should clear Quantiser controller state and remote MIDI descriptors after a safe handoff. Do not solve this with `_sceneMutex` on the callback.
- **Protected timing concepts affected:** local timing clear, remote authority/connected state, active/remote MIDI grid, `NoSync` invalidation, immutable station membership.
- **Verification:** targeted two-thread test repeatedly connecting/disconnecting and adding/removing the last local take while callbacks execute; TSAN/equivalent when available; assert no callback reaches `HasConnectedTiming`, raw `_stations`, `_masterLoop.reset`, `_preReclockTakeIds.clear`, or a lock; empty connected session must preserve accepted remote timing while empty disconnected session clears local timing as intended.
- **Human decision:** pending.

### S07-03 — Publish a coherent local Timer transport snapshot for job-thread timing decisions

- **Stage / reviewer:** Stage 7 — thread safety.
- **Scope reviewed / exclusions:** compound-state consistency across threads, not the numerical formulas (Stage 11) or follow-policy behavior (Stage 9).
- **Severity:** must fix before merge.
- **Evidence:** Timer exposes interval length, loop count, phase, absolute position, and scene coordinate as separate atomics (`Timer.h:69`–`:85`, `:97`–`:114`). The audio callback changes several fields in `Timer::ApplyCommand` (`Timer.cpp:205`–`:237`) and advances scene/count/phase in `Timer::Tick` (`:40`–`:58`). On the job thread, `NinjamTimingCoordinator::Observe` independently reads `SeedSourceLength`, `SampOffset`, and `AbsoluteSamplePos` at `NinjamTimingCoordinator.cpp:216`–`:240`; `AbsoluteSamplePos` itself combines three separate loads at `Timer.h:75`–`:82`. Acquire/release on individual fields prevents undefined behavior but supplies no version proving all values came from one audio boundary. History `d6fdb88` introduced the unified command, but the coordinator still reads live Timer state across the thread boundary.
- **Why it matters:** A replacement or wrap between those loads can pair an old phase/count with a new interval, making the job thread calculate observation age or signed correction in a geometry that never existed. That undermines the branch's central guarantee that authority and coordinate conversions remain coherent even though no scalar data race occurs.
- **Recommended disposition:** publish one versioned immutable local-transport observation from the audio boundary containing every coordinator input (scene coordinate, local master length/phase or absolute anchor, and device sample anchor). Have the coordinator consume that value rather than query mutable Timer fields piecemeal. Keep Timer mutation audio-owned and preserve the distinction between Timer absolute, scene, and device coordinates.
- **Protected timing concepts affected:** local master transport, master phase, Timer absolute sample, monotonic scene coordinate, device observation anchor, remote/local correction.
- **Verification:** concurrent sentinel-generation test that alternates incompatible Timer geometries and proves the coordinator never receives a mixed tuple; replacement-at-read-boundary integration case; existing late-observation, reconnect, unequal-length, and `NoSync` tests.
- **Human decision:** pending.

### S07-04 — Make the timing-command producer contract explicit and self-enforcing

- **Stage / reviewer:** Stage 7 — thread safety.
- **Scope reviewed / exclusions:** writer ownership and future race resistance; moving command materialization remains the approved F-009 structural work.
- **Severity:** follow-up.
- **Evidence:** `NinjamAudioTimingCommandMailbox` declares a single “job thread” writer at `NinjamAudioTimingCommand.h:31`–`:34`, `:53`–`:57`. Production publishers include the job loop (`Scene.cpp:1387`–`:1396`) but also UI/main-thread connect/disconnect (`Scene.cpp:254`–`:305`) and prompt resolution (`Scene.cpp:394`–`:400`). Current calls are mutually excluded by `Scene::_sceneMutex`, so no present data race was proven, but the mailbox does not encode or assert that external serialization. Existing command-mailbox tests are sequential (`NinjamAudioTimingCommand_Tests.cpp:32`–`:93`); only the observation mailbox has a concurrent writer/reader test (`NinjamTimingObservationMailbox_Tests.cpp:69`–`:109`). The unified mailbox arrived in `d6fdb88`.
- **Why it matters:** Correctness relies on a lock and call-site discipline outside the mailbox while its documentation communicates a different ownership model. A later caller following the public `AudioHost::PublishTimingCommand` API (`AudioHost.h:70`–`:76`) can introduce concurrent producers and invalidate the odd/even writer protocol.
- **Recommended disposition:** as part of F-009, establish one NINJAM integration/job producer and route UI intent to it, or explicitly implement/document a serialized multi-producer publication mechanism outside the callback. Keep the audio reader lock-free. Add a concurrency/ownership test and restrict the public publication surface.
- **Protected timing concepts affected:** command lifecycle and generation only; do not split Timer and per-entity fan-out.
- **Verification:** producer call-site audit; job/UI overlap test or single-owner assertion; concurrent writer/reader test appropriate to the chosen contract; existing latest-wins/invalidation integration tests.
- **Human decision:** pending.

## Uncertainties

- The bundled NJClient header gives a clear thread-affinity rule but its implementation source is not present. Therefore S07-01 does not claim a particular internal non-atomic member race; it establishes an unsupported concurrent API use and absence of a Jamma-side coherent publication. That is sufficient to reject the current audio-thread getter path.
- `MidiClockAnchor` uses a relaxed first sequence increment (`MidiClockAnchor.h:21`–`:29`) whereas the newer timing mailboxes use release/acq_rel for the transition to odd. No failing execution or data race was demonstrated because all payload fields are atomic. A dedicated memory-model/TSAN test should be added before changing it; Stage 11 may decide whether a common snapshot primitive is warranted.
- `LocalTransportOffsetLoopFracMailbox` is documented as UI-writer/audio-reader and all found production calls fit that model after initialization, but no concurrent test proves it. If future MIDI/job control publishes it, its writer ownership must be revisited.
- No build, native test, runtime session, sanitizer, or concurrency stress run was performed in this read-only investigation. Existing tests prove functional mailbox behavior and one observation-mailbox concurrency case; they do not close S07-01 through S07-04.

## Conclusion

Stage 7 found four evidence-backed candidates: one merge blocker, two must-fix-before-merge concerns, and one follow-up. The immutable station snapshots, audio-confined phase maps, observation mailbox, applied-command receipt, connection-use pin, and per-entity atomic anchors are consistent with the repository's publication pattern. The phase cannot claim an accepted concurrency model yet because the audio callback calls forbidden NJClient getters, the empty-scene reset crosses into unsynchronized coordinator/Scene state, and job-thread timing decisions read a non-versioned compound Timer state. These findings require canonical integration and explicit human decisions; no runtime cleanup is authorized by this report.
