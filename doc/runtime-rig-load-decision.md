# Runtime rig loading: phase 5 decision

**Decision:** Defer a runtime **Load Rig** action. The current code supports JAM-file replacement using the accepted rig, but it does not provide a small path for replacing the rig while preserving an unsaved, in-memory JAM. This is the bounded outcome of phase 5 of the alpha checklist repair plan.

## Concrete path and gaps

1. **Select and validate.** Startup reads a `.rig`, parses it with diagnostics, and applies `StartupConfig::ValidateRig` ([Main.cpp](../Jamma/src/Main.cpp), lines 376–394, 618–630). A runtime picker and preflight could reuse that validation before touching the current Scene. The existing picker is JAM-specific ([PathUtils.cpp](../JammaLib/src/utils/PathUtils.cpp), lines 164–202). Cancellation must leave the current Scene, rig revision, devices, and default paths untouched, as the JAM picker does before admission ([Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 4687–4695; [Main.cpp](../Jamma/src/Main.cpp), lines 1143–1149).
2. **Preserve the live JAM.** The current load path builds `Scene::FromFile` from a selected JAM file and the *accepted current rig*, retains the old Scene on construction failure, then shuts it down and swaps the window Scene ([Main.cpp](../Jamma/src/Main.cpp), lines 1151–1185). There is no in-memory JAM capture on that path. `IoSessionExporter` captures live state only inside a directory export that numbers/writes a JAM and assets ([Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 4824–4839; [IoSessionExporter.cpp](../JammaLib/src/io/IoSessionExporter.cpp), lines 76–107, 235–280, 302–320). Using the last saved JAM would discard unsaved takes and edits; forcing Save would change persistence semantics. A runtime rig load needs a detached, complete, temporary session capture that can feed reconstruction without writing or changing the save folder.
3. **Stop capture and exclude producers.** Save and Load currently reject active or pending capture, including trigger and take state ([Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 4524–4534, 4670–4702). Load closes rig trigger input, waits for the job acknowledgement, takes the lifecycle writer lock, quiesces audio, suspends MIDI dispatch, and releases live notes before the final capture check ([Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 4807–4858). There is no operation here that finishes or ditches capture on the user's behalf. A safe new flow must either wait/reject without changing capture or define and test an explicit capture-stop transaction; it cannot treat callback pause as capture completion.
4. **Reconstruct and publish.** `IoSessionLoader::Reconstruct` builds stations from saved descriptors and assets, and `Scene::FromFile` builds the initial rig against those stations, restores trigger histories and timing, and publishes station/audio/input/HUD state ([IoSessionLoader.cpp](../JammaLib/src/io/IoSessionLoader.cpp), lines 11–75; [Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 375–455). In-place `RigCoordinator::SubmitCandidate` rejects any `User` hardware/settings change with `ReinitialisationRequired` ([RigCoordinator.cpp](../JammaLib/src/engine/RigCoordinator.cpp), lines 210–237). Its ordinary publication transfers trigger take histories only for staged trigger replacements after the audio boundary ([RigCoordinator.cpp](../JammaLib/src/engine/RigCoordinator.cpp), lines 328–371); it is not a whole-Scene reconstruction API. A full replacement must preserve the old Scene until the candidate is ready, prevent input/audio races across the swap, then retire the old Scene through its shutdown order ([Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 3082–3143).
5. **Handle hardware failure.** Runtime audio reconfiguration can fail after stopping the previous backend; it attempts to reopen the prior stream, but may leave admission blocked if teardown or restoration fails ([AudioHost.cpp](../JammaLib/src/audio/AudioHost.cpp), lines 454–553). Existing Scene audio controls also reject a sample-rate change while takes exist and refresh rig availability only after a successful reconfiguration ([Scene.cpp](../JammaLib/src/engine/Scene.cpp), lines 4537–4546, 4865–4919). A selected rig with different hardware therefore needs an explicit commit/rollback boundary for device, MIDI, rig, and Scene state, including a stopped/error outcome if the old backend cannot be restored. Building a candidate Scene alone does not provide this guarantee.

## Required future contract

Implement a capture/replacement coordinator outside `Scene.cpp` that (a) preflights the chosen rig and detached live JAM, (b) declines or explicitly finishes capture before quiescence, (c) constructs the candidate with the selected rig and the captured JAM, (d) commits Scene and hardware publication together or restores the old Scene, and (e) reports recovery failure without claiming the old audio is running. Test unsaved content, pending/active capture, picker cancellation, invalid rig, hardware-change failure with rollback, and paired JAM+rig reload. Keep ordinary JAM loading's active-rig behavior explicit until a paired-load choice exists.

Rig persistence stays independent: **Save** targets the current rig path, **Save As** chooses a path, and **Save rig as default** alone updates startup defaults ([RigDefaultSave.h](../Jamma/src/RigDefaultSave.h), lines 64–112). Loading must not silently save a rig, rewrite defaults, or conflate the two file paths; startup already treats selected JAM and rig paths separately ([Main.cpp](../Jamma/src/Main.cpp), lines 594–630, 921–934).
