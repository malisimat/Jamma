## System understanding

Remote timing enters as NJClient-owned signed position/length plus sample rate, BPM, and BPI. Jamma converts negative position/rate/BPI values to zero and applies the shared `IsValidRemoteTiming` boundary on both current live and periodic snapshot paths (`NinjamConnection.cpp:709`–`:733`, `:922`–`:946`). Ordered BPM comparisons reject NaN and infinities; BPM and BPI are bounded to 20–400 and 1–32. Valid observations are converted into fixed-size value contracts and ultimately consumed at an audio boundary. This is an O(1) timing-data path; remote timing does not itself allocate a collection proportional to a network-provided length.

The authority transition is nevertheless not fail-closed after authority has been accepted. Invalid observations return no coordinator update (`NinjamTimingCoordinator.cpp:68`–`:77`), and absent snapshots are hidden (`NinjamSession.cpp:452`–`:463`). Accepted F-027/F-028 therefore remain the controlling findings: malformed/absent timing must produce one complete `NoSync` authority-loss transition and later recovery must require a fresh valid epoch. Stage 18 adds no competing invalidation mechanism.

Local seed timing is also part of the remote-join trust chain because it can be pushed to a server. User configuration supplies millisecond/BPM policy values, Quantiser derives local geometry, Scene publishes that geometry to the coordinator on connect, and `NinjamConnection::RequestServerTempo` formats it into bounded chat commands. This path is normally finite and small, but two public conversion/egress seams and one extreme configuration conversion do not make that precondition self-enforcing.

Portable `.jam` data crosses a stronger boundary than ordinary in-memory timing. It contains NINJAM host, user, password, and work directory. Loading can auto-start a session, and exporting a session copies the controller's full NINJAM config into a user-selected `session.jam`. Those are security/robustness contracts, not timing coordinates. Correcting them must not persist live remote authority, session epoch, map, anchors, generation, or phase.

Timing-relevant MIDI ingress is bounded: messages are reduced to three fixed bytes, timestamps use Jamma's steady clock and saturating sample conversion, each queue has compile-time capacity 1024 with drop-newest behavior, the immediate dispatcher processes at most 1024 events per pass, and remote MIDI grid geometry derives from the already validated remote interval/BPI. Those mechanisms preserve local MIDI event cursor and automation origin as distinct from remote master phase.

## Candidate findings

### S18-01 — Complete F-032 at both numeric conversion and network serialization boundaries

- **Stage / reviewer:** Stage 18 — security and input robustness; refines accepted F-032/S11-04 rather than requesting a second canonical finding.
- **Scope reviewed / exclusions:** malformed/non-finite BPM/BPI at Jamma-owned helper and outgoing NINJAM command seams. Ordinary tempo arithmetic is Stage 11; server acknowledgement policy is Stages 9/10.
- **Severity:** follow-up hardening (accepted F-032 severity).
- **Evidence:** `IntervalSampsFromTempo` checks only `bpm <= 0`, zero BPI, and zero rate before a floating-to-`unsigned int` conversion (`JammaLib/src/ninjam/NinjamTiming.h:126`–`:138`, commit `d0d208e`). Accepted F-032 already proves NaN bypasses that guard. The same incomplete predicate exists at the egress seam: `NinjamConnection::RequestServerTempo` checks `bpm <= 0.0f || bpi <= 0`, then formats and sends four admin/vote messages (`JammaLib/src/ninjam/NinjamConnection.cpp:742`–`:779`, commits `87900d6`, `a1107e7`, `63adae4`). NaN or positive infinity bypasses the guard and serializes as implementation-formatted non-numeric text. Current production local geometry is finite, so this is defense in depth, but neither public seam states or enforces that precondition. Existing tests cover zero and ordinary values only (`test/JammaLib_Tests/src/ninjam/NinjamTiming_Tests.cpp:129`–`:132`; `test/JammaLib_Tests/src/engine/Quantisation_Tests.cpp:80`–`:83`).
- **Why it matters:** future callers or corrupted in-memory/config values can turn malformed numeric state into undefined/implementation-dependent conversion or invalid server commands. Validation at only the inbound NJClient observation path does not protect locally generated outbound data.
- **Recommended disposition:** enrich F-032 so the Jamma-owned tempo value boundary rejects non-finite and out-of-product-range values before arithmetic or string formatting. Use the existing plausible BPM/BPI constants where the operation claims to speak NINJAM; retain saturating behavior for large but valid sample products where intentional. Do not modify NJClient or add a new class.
- **Protected timing concepts affected:** local requested BPM/BPI, remote observed BPM/BPI, and derived interval samples remain distinct.
- **Verification:** table-driven NaN, ±infinity, zero, negative, plausible endpoints, just-outside endpoints, and extreme finite BPM/BPI/rate cases. Assert helper failure is zero, outgoing request returns false and sends nothing, and valid endpoint formatting remains stable.
- **Human decision:** pending Phase 3 gate; canonical integration should update F-032 rather than allocate a new finding.

### S18-02 — Bound seed-timing policy before floating-to-Windows-integer conversion

- **Stage / reviewer:** Stage 18 — security and input robustness.
- **Scope reviewed / exclusions:** hostile/extreme timing policy in local user configuration because it feeds local geometry and optional remote tempo push; no broad configuration-schema redesign.
- **Severity:** must fix before merge.
- **Evidence:** `UserConfig::LoopSettings::FromJson` accepts any JSON `unsigned long` for `seedGrainMinMs`, `seedGrainTargetMaxMs`, and `seedBpmMin` with no product bound (`JammaLib/src/io/UserConfig.cpp:176`–`:222`, commits `923af30`/`fa8d7cf`). `Quantiser::MinSeedSamps` safely clamps one `sampleRate * minMs / 1000` result through `_RoundedToUInt`, but `DeduceSeedTiming` separately computes `sampleRate * targetMaxMs / 1000` as `double` and casts it directly to `unsigned long` (`JammaLib/src/engine/Quantiser.cpp:686`–`:735`, commit `c019569`, moved by `e2dc3f8`). On supported Windows, `unsigned long` is 32-bit. At the normal 44.1 kHz rate and `targetMaxMs=UINT32_MAX`, the value is about 189,408,057,709 samples, far outside that type; C++ floating-to-integer conversion outside the destination range is undefined. This path is reached when configured policy derives first-loop/local tempo geometry (`UserConfig.cpp:480`–`:502`; `Quantiser.cpp:467`, `:705`–`:734`) that can later become Scene's local tempo request (`Scene.cpp:254`–`:264`). Tests use only ordinary 400–5000 ms policies (`UserConfig_Tests.cpp:29`–`:38`, `:134`–`:156`, `:203`; `Quantisation_Tests.cpp:68`).
- **Why it matters:** a syntactically valid but extreme local config can make loop/timing derivation undefined before the system has a chance to fail closed. The result may corrupt geometry that is later used locally or offered as remote tempo authority.
- **Recommended disposition:** validate/clamp the policy at its existing owned config/Quantiser boundary and use the same checked/saturating conversion for both minimum and target-maximum products. Reject impossible policy relationships deterministically rather than accepting an implementation-specific cast. Keep local seed geometry separate from remote authoritative geometry and add no new class.
- **Protected timing concepts affected:** local grain/seed policy, local master geometry, requested local BPM/BPI, and remote authority remain distinct.
- **Verification:** parse and derive with defaults, zero, `UINT32_MAX`, the exact last product that fits, and the first product that exceeds `uint32`; test min greater than target max and maximum sample rate. Assert deterministic reject/clamp, no undefined conversion, finite local BPM, nonzero internally consistent seed/count/master, and no malformed tempo request.
- **Human decision:** pending Phase 3 gate.

### S18-03 — Do not copy NINJAM passwords into portable exported sessions

- **Stage / reviewer:** Stage 18 — security and input robustness.
- **Scope reviewed / exclusions:** sensitive NINJAM session-config serialization only. Well-formed schema compatibility remains Stage 16; no general credential-store redesign is proposed.
- **Severity:** must fix before merge.
- **Evidence:** `JamFile::NinjamConfig` includes `Pass` (`JammaLib/src/io/JamFile.h:45`–`:55`, commit `f98b734`), its parser loads `"pass"` (`JamFile.cpp:469`–`:509`), and `ToStream` always emits it as cleartext JSON (`JamFile.cpp:368`–`:377`, commit `1a8bcd9`). Session export copies `ninjamController->Config()` wholesale into the export model, then writes it to the user-selected `<exportDir>\session.jam` (`JammaLib/src/io/IoSessionExporter.cpp:50`–`:60`, `:132`–`:140`, commit `fe023bb`). The action is described as exporting loops plus a portable session, and there is no warning/redaction or distinction between restart-only local secrets and shareable session state. Reviewed timing/connect logs print host/user but not `_pass` (`NinjamConnection.cpp:205`–`:214`).
- **Why it matters:** a non-anonymous user's NINJAM credential is silently copied into a file likely to be archived, backed up, or shared with exported audio. This is a concrete confidentiality failure even though runtime logging itself avoids the password.
- **Recommended disposition:** exclude `Pass` from exported `session.jam` and make reconnect prompt/load credentials from an explicitly local trusted setting if authenticated sessions must persist. If the normal private default `.jam` is intended to retain a password, make that a separate explicit product decision and ensure export never inherits it. Do not serialize remote authority, epochs, maps, anchors, or live timing state as a workaround.
- **Protected timing concepts affected:** none; session credentials are not remote timing authority.
- **Verification:** export a controller config containing sentinel host/user/password/workdir; inspect `session.jam` to prove the password sentinel is absent while approved non-secret identity/timing fields round-trip. Load the export and verify it cannot authenticate silently; anonymous empty-password sessions remain usable according to the human decision.
- **Human decision:** pending Phase 3 gate.

### S18-04 — Remove portable `.jam` authority to create and select arbitrary NJClient work directories

- **Stage / reviewer:** Stage 18 — security and input robustness.
- **Scope reviewed / exclusions:** NINJAM work-directory trust and failure behavior. Generic application path pickers and resource paths remain excluded.
- **Severity:** must fix before merge.
- **Evidence:** `NinjamConfig::FromJson` accepts any string as `WorkDir` (`JammaLib/src/io/JamFile.cpp:469`–`:509`, commit `f98b734`). Persisted load passes it unchanged through `NinjamSession::Start` into `NinjamConnection` and auto-connects (`JammaLib/src/ninjam/NinjamSession.cpp:383`–`:417`, commits `34e9693`/`62739cf`). Every connect calls `_EnsureWorkDir`; a non-empty supplied path is sent directly to `std::filesystem::create_directories`, all exceptions are swallowed, and the same path is then passed to `NJClient::SetWorkDir` (`JammaLib/src/ninjam/NinjamConnection.cpp:171`–`:215`, `:816`–`:838`, commit `f98b734`). There is no canonicalization, allowed-root policy, path-length check, trust marker, or proof creation succeeded. Stage 16 additionally proves the shipped persisted/default path starts network work immediately without the interactive timing-start path.
- **Why it matters:** merely loading a crafted portable session can attempt filesystem creation outside Jamma's app-controlled temporary/session directories and direct upstream remote-file activity there. Silent failure also leaves the upstream behavior for an invalid/uncreatable path unclear. The file author, not the local user/application policy, currently selects this sink.
- **Recommended disposition:** treat portable `WorkDir` as untrusted/non-authoritative. Prefer the existing app-controlled temp fallback for loaded/exported sessions; if a custom directory is a supported expert setting, obtain it from an explicit local trusted configuration/picker, canonicalize it, enforce a documented allowed-root policy, and fail the connection visibly if preparation fails. Keep this in the existing NINJAM/session owner and do not edit NJClient.
- **Protected timing concepts affected:** none directly; work directory is not a clock, coordinate, follow policy, or session epoch.
- **Verification:** crafted `.jam` cases for absolute paths, relative traversal, UNC/device-like paths, overlong/invalid paths, unwritable roots, symlink/reparse traversal where practical, and the empty default. Assert no filesystem mutation occurs outside the approved root, NJClient is not started with a failed/untrusted path, and the normal temp directory still connects.
- **Human decision:** pending Phase 3 gate.

## Uncertainties

- The bundled repository contains only NJClient's public header and compiled libraries. Its parser, maximum remote user/channel counts, string ownership/length limits, work-directory fallback, and exact `Run()` work budget cannot be audited. The report therefore relies on Jamma-observable contracts and does not speculate a canonical finding from absent implementation.
- The supported product policy for a non-empty NINJAM password is undocumented. S18-03 proves portable export disclosure regardless: even if a private app-owned config may retain a secret, a user-selected session export should not silently copy it.
- The intended semantics of a non-empty portable `workdir` are also undocumented. S18-04 does not assume all custom paths are forbidden; it requires the authority to come from an explicit local trust decision rather than a loaded/shareable file, with deterministic failure.
- `IsValidRemoteTiming` does not independently cap interval length/source rate or prove their consistency with BPM/BPI. Upstream getters return signed `int`, conversion is saturating, and production source rate is tied to audio setup; no memory allocation is sized from the remote interval in the reviewed live timing path. Without upstream construction evidence, this remains a contract-hardening consideration rather than a new finding. F-032 verification should still include extreme finite combinations.
- Generic JSON reads, remote server-directory HTML, chat/user names, and verbose MIDI packets can all consume or emit attacker-influenced strings. Their broad remediation would exceed the timing-only gate. The exact inherited `.jam` limit gap is recorded above so the exclusion is explicit rather than mistaken for certification.
- No hostile runtime evidence was executed. S18-02 is language/width-certain on Windows; S18-03/S18-04 follow direct serialization/path call chains. Runtime tests are still required before cleanup.

## Conclusion

Stage 18 completed the bounded timing/NINJAM input audit and found four candidate groups. Accepted F-032 should be completed at both tempo conversion and outgoing command serialization (S18-01). Extreme but syntactically valid local seed policy can reach an out-of-range floating-to-32-bit-Windows-integer conversion before the value becomes local/remote tempo geometry (S18-02). Portable session export silently includes a cleartext NINJAM password (S18-03), and a loaded `.jam` can select/create an arbitrary NJClient work directory without an explicit local trust decision or deterministic failure (S18-04).

Remote timing scalar ingestion otherwise has a shared finite/plausibility boundary and fixed-size publication. Timing-relevant MIDI timestamps/queues are bounded and saturating. The critical malformed/absent authority response is still the already accepted F-027/F-028 complete `NoSync`/fresh-epoch recovery, not a new security-specific state machine. Generic JSON file/depth limits and unverifiable upstream user/channel/job-work bounds remain explicit residuals, not claims of security certification.

No protected timing concept is collapsed: remote observation, local timing, Timer geometry, scene/device coordinates, mapped elapsed time, per-entity phase/anchors, remote grid, MIDI cursor/automation origin, follow policy, and session epoch remain distinct. No cleanup, source edit, test rewrite, upstream change, or unrelated retained-feature modification was performed.
