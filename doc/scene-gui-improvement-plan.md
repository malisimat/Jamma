# Scene GUI improvement plan

Planning baseline: current code inspected on 6 October 2026. This document proposes implementation work; no implementation changes accompanied it. Line references below describe this baseline and will drift as work lands.

Review status: checked against the current Scene, HUD, control, rendering, and timing paths. The direction is sound, subject to the integration contracts below. The initial feature relocates working controls and improves presentation; Session actions, Groups, device selectors, and numeric BPM entry are follow-ups unless separately verified and scoped. No runtime or visual performance claim is made by this document review.

## Agreed outcome

- Expanded panels overlay the scene. Collapsed panels retain a clearly labelled, clickable tab/handle so their existence is obvious.
- The top settings panel contains only the selection-depth radio for now. The input HUD (GuiHud) remains a separate component; “only selection depth” does not remove input routing from the screen.
- Replace the bottom-left demo panel with real settings, selected through radio tabs. Move global MIDI quantisation, MIDI channel override, and the existing transport-offset input into it. Retain the existing CLICK function in the timing page.
- Use the existing GUI control library. Panel composition, presentation helpers, and command bindings may change; no new control primitive or external UI toolkit is required.
- In the GuiHud, input boxes/cards stay in a single horizontal row. Adapt their widths to fit, with an approximately 80 px minimum, then use the existing scrollable parents. Trigger cards retain their fixed height while their viewport resizes.
- Use translucent grey backgrounds, restrained futuristic borders, and time-based slide/alpha easing.
- No persistence of panel positions, open states, sizes, or selected tabs in this feature. Preserve existing session/rig persistence behavior.
- Audio/MIDI device selection (in the new collapsable panel bottom-left) is a future use of the panel framework, explicitly outside this feature's wiring scope. Provide page/composition slots; do not implement device switching, enumeration UI, or Apply actions here.
- Connected cables remain drawable when stations or scrolled input/trigger sockets are outside the visible region. Off-panel render endpoints terminate at the appropriate visible boundary.

Proposed defaults, rather than additional requirements: start both settings panels expanded; slide the top panel upward and the bottom-left panel leftward. Keep reopen tabs on their window edges. These choices can be tuned during visual review.

## Ownership and layout

Keep Scene as presentation/wiring orchestrator, in accordance with [glossary.md](glossary.md). Panel classes compose widgets and expose user intent; device lifecycle, session I/O, selection operations, and timing retain their existing owners. Avoid putting engine policy into `GuiMainPanel`.

Establish one coherent overlay layout calculation using actual window dimensions, margins, occupied HUD bounds, and panel state. Use existing `GuiPanel`, `GuiStackPanel`, `GuiGrid`, and `GuiScrollPanel` to express the resulting layout. Do not build a new general-purpose docking framework.

- Anchor the selection panel to the top edge and the settings panel to the bottom-left edge. Positions use Jamma's bottom-origin overlay coordinates; a top anchor therefore changes Y with window height.
- Keep persistent reopen tabs within the actual viewport, including while resizing mid-animation. Account for the input strip and right trigger rail so handles remain discoverable.
- Bound expanded settings panels to the available window area. Scroll page content when necessary rather than enlarge an imaginary window. Use signed, clamped intermediate arithmetic to avoid unsigned underflow in tiny windows.
- Overlay backgrounds consume pointer input inside their visible bounds. Empty screen space continues to reach scene interactions. Popup menus render and receive input above panels; controls must not click through to stations.
- Make draw order and input priority agree explicitly. Scene currently draws `_guiChildren` before station overlays and the selector (`Scene.cpp`, lines 700–715), and gives loop-editor, Shift/master-selection, and quantisation gestures opportunities before normal GUI dispatch (lines 919–963). Render scene/editor content below the settings overlays and popups above them. An existing pointer capture retains its gesture until release/cancel; otherwise visible panel bounds arbitrate before scene gestures, including wheel events and modifier clicks. Check the special loop-editor HUD path as well as normal dispatch. Do not rely on reparenting or child order alone to establish this contract.
- Reparenting must reconcile standalone radio draw, resource, hover, focus, and touch paths. Scene currently draws radios separately at lines 711–712, initializes/releases them separately at lines 865–889, dispatches touches at lines 1043–1059, and explicitly wires receivers at lines 1889–1898. Choose one ownership/routing path and remove duplicate dispatch/drawing.
- Separate command identity from tree position. `GuiElement::Init` renumbers children, and `AddChild` reruns initialization ([GuiElement.cpp](../JammaLib/src/base/GuiElement.cpp), lines 69–80 and 610–621). Directly reparenting controls can therefore overwrite Scene's action IDs. Prefer a small panel-owned receiver adapter that maps local controls to explicit user intents and forwards them to existing Scene handlers. Keep legacy IDs at that boundary rather than rewriting generic tree indexing; verify bindings after the final composition and later child additions. Scene may retain non-owning access or shared references for state synchronization, with one tree responsible for drawing/resources/input.
- Hidden pages must neither draw nor accept input. Closing a panel or switching pages should clear obsolete hover/focus and safely resolve active edit/capture state. Keep widget values synchronized with their real owners, including changes made by shortcuts.
- Define that resolution before hiding: finish a valid pending numeric edit through its normal validation path, revert invalid text, cancel pointer drags without synthesizing a click, and clear Scene capture and the affected subtree's transient states. Existing settings notify on text change, not only Enter ([GuiTextBox.cpp](../JammaLib/src/gui/GuiTextBox.cpp), lines 201–225); retain that behavior and reconcile the displayed value with its owner. `ClearFocus` is not a numeric commit API, so use a small explicit edit-finalization hook if needed rather than fake keyboard events. `SetVisible` alone only flips a flag (`GuiElement.cpp`, lines 367–375); it does not clear descendant focus or capture. Close popups owned by the hidden subtree without dismissing unrelated modal prompts. Consume the terminating release so Scene's unconditional selector update on touch-up (lines 994–998) cannot turn closing a panel into a scene action.
- For tiny or zero-sized client areas, keep geometry non-negative and skip empty draw/hit regions. At usable sizes prioritize reopen handles, then header/tabs and scrolling content. Define the smallest supported interactive size during visual review; it is impossible to keep every header/footer/control usable in arbitrarily small windows. Do not manufacture positive off-window viewports to disguise that limit.

## Bottom-left production pages

Start on Timing so the relocated controls are immediately discoverable. A Tap button is a small optional slice using the verified existing path. Keep composition slots for **Audio**, **Session**, and **Groups**; add their tabs when they have working actions. Existing buttons, toggles, dropdowns, numeric inputs, sliders, labels, grids, and scroll panels suffice. If tabs cannot fit, use the existing horizontal scroll composition rather than introduce another tab control. Keep the tab strip/header independent of scrolling page content.

Use one active page host with retained widget state and explicit page bounds. Check parent visibility/enabled gates in overridden hit paths too; `GuiStackPanel::RouteHitTest` can fall back to its children after the base rejects a hit. Keep inactive pages out of layout/input traversal without rebuilding their controls on every switch, and preserve/clamp page scroll offsets.

## Responsive input HUD and triggers

Use the available input area after actual margins and the trigger rail. Remove the nominal input-strip width as an unconditional ceiling. Allocate audio/MIDI viewports deliberately; avoid reserving an arbitrary fraction for an empty category.

For each populated row, subtract padding and gaps, divide the remaining width across its cards, and clamp the result to an approximately 80 px minimum. A modest preferred/maximum width can stop a lone input becoming comically enormous. When minimum widths overflow, size the content to its full logical width and scroll inside the existing parent. Keep wrapping disabled. Retaining the separate audio/MIDI scroll parents is the least disruptive baseline; do not merge them merely to obtain adaptive widths.

Changing width must also update label frames, socket centers, meters, content size, scrollbar metrics, and cable geometry. Replace fixed eight-character label splitting with width-aware measurement and sensible truncation; one or two text lines may still fit inside each card without wrapping the card row itself. Preserve current scroll offsets where valid and clamp after resize/rebuild.

Resize existing card widgets in place where possible. `GuiScrollPanel::SetContent` resets the offset ([GuiScrollPanel.cpp](../JammaLib/src/gui/GuiScrollPanel.cpp), lines 49–65), so replacing a content tree requires an explicit save/restore/clamp and interaction cleanup. Measure/truncate labels when text, width, or resolved font changes, using existing glyph advances; do not rebuild fonts, labels, or widget trees every animation frame. Keep a way to inspect the full device identity through existing UI composition when names are truncated, and keep available/unavailable state readable without relying on colour alone.

The trigger rail should follow window height and its right edge without relying on artificial minimum viewport dimensions or unexplained offsets. Keep current 100 px trigger height, header/footer space, Add/Delete behavior, routing status, and reveal-newest behavior. For a very short window, reduce the visible viewport rather than compress the cards.

## Cables to off-panel targets

Separate three concepts: logical route identity, real socket/anchor position, and presented cable endpoint. `_BuildInteractionGeometry` currently entangles all three and is reused for drawing and editing. Extend/refactor that representation only enough to preserve existing routing semantics.

1. Build connected cable records from routing state regardless of whether their socket is scrolled into view. Missing targets and unavailable devices remain distinct from merely clipped targets.
2. Resolve a true content-visible rectangle for each scroll parent. Extract one small rectangle/transform helper from its drawing path ([GuiScrollPanel.cpp](../JammaLib/src/gui/GuiScrollPanel.cpp), lines 203–236) and reuse it for content hit tests, HUD socket drawing, and cable resolution. Existing `_IsInViewport` and HUD socket scissors duplicate parts of this calculation. Include padding, scrollbar exclusion, content-host scroll transform, ancestor clipping, and window clipping. Convert everything into one coordinate space, preferably HUD-local.
3. Keep visible endpoints at their actual positions. Project off-panel ones to the relevant visible boundary, using a consistent clamping/intersection rule. Horizontal source rows terminate at left/right edges; trigger sockets above/below their viewport terminate at top/bottom edges. Account for nested clipping and window clipping. Preserve cable fanning without pushing edge endpoints outside the rectangle.
4. For stations, retain valid projected anchors beyond every window edge and resolve them to the scene viewport boundary. Replace the `X < -1000` magic sentinel with explicit projection validity. `Scene::_UpdateHudStationAnchors`, lines 2475–2503, currently checks only `abs(w)`; check finite clip coordinates and the camera's front/near-plane convention before division. Keep projected positions in floating point until boundary resolution has bounded them, then convert to integer pixels. Invalid/behind-camera anchors have no trustworthy screen direction: retain the logical route but omit that cable's presentation until a valid anchor returns, rather than invent a jumping endpoint.
5. Render curves using the resolved endpoints, outside content scissor scopes but within the window viewport. Keep the current reveal/hover/loop-editor policy (`_CableVisible`, line 981); being off-panel must not independently remove a connection. Resolve both ends when both are clipped.
6. Keep real socket hit targets restricted to their visible areas. Boundary continuation markers are decorative, with no socket hit/snap candidates. Preserve grabbing of visible cable bodies using the displayed curve and existing original route handle/fixed-end identity; feed endpoint snapping only real visible sockets. Rendering and hit testing must use the same curve/control points, not separately approximated edge curves. Preserve revision checks, pending routing edits, and unavailable-source behavior; cancel stale drags on graph replacement rather than reconnect to an entity now occupying the same index.

Mark edge continuations with a small notch or subdued arrow using existing rendering/assets. Boundary clamping should transition continuously into the true socket as it enters view; do not add independent endpoint easing that disconnects a cable from a visible socket. Recompute after scrolling, camera movement, resize, source/trigger rebuild, and relevant panel transitions. An empty effective viewport retains logical routes but has no renderable endpoints or hit targets until space returns. Panel occlusion is separate from scrolling: settings draw over cables and prevent cable grabs beneath their visible bounds; it does not reroute connections to arbitrary settings-panel edges.

## Visual treatment and motion

Suggested direction: smoked graphite fills at roughly 70–85% opacity, thick angled/chamfered cool-grey borders, clipped-corner accents, and short cyan highlights for active page/focus. Use warm amber for selected timing options, red for mute/error, and subdued grey for unavailable controls. Preserve semantic differences in capture/station cables and MIDI lane colours; consistency does not mean painting every state cyan.

Centralize a small set of GUI style values/presets and apply them to related controls. Existing colours are scattered through Scene/HUD construction and `GuiMainPanel` demos. Prefer existing nine-patch/rounded assets and thin decorative elements; do not require generated artwork or a new theme engine.

Use elapsed-time easing, with a starting duration around 180–250 ms. One normalized transition value drives panel position and opacity. Reversing mid-slide begins from the current value; resizing recomputes anchors without restarting the transition. Reopen tabs remain visible and independently interactive. Decorative motion must not delay device/session actions.

Advance motion once per UI frame using a monotonic wall clock, before hover resolution and drawing. `Window::Render` resolves deferred hover before `Scene::Draw` ([Window.cpp](../JammaLib/src/graphics/Window.cpp), lines 491–531); moving widgets only inside Draw would leave stationary-pointer hover one frame behind. Invalidate hover when bounds change, clamp long elapsed intervals after minimize/resume, and reuse the current layout on pointer dispatch. Never drive easing from the audio clock or `Scene::OnTick`. Gate closing page content against new presses immediately while retaining the visible background blocker and reopen handle through the slide; opacity alone must never determine hit testing.

There is no verified general subtree-opacity feature: `GuiElementParams` supplies RGB tint, and [texture_tinted.frag](../Jamma/resources/shaders/texture_tinted.frag) multiplies RGB while leaving texture alpha unchanged. [font.frag](../Jamma/resources/shaders/font.frag) uses glyph coverage for alpha. Plan a small scoped opacity propagation through existing rendering paths, with default 1 and restoration after each subtree. Cover text, textures, and any panel-owned decorations; avoid uniform state leaking into later HUD/scene draws. This rendering support is required for the requested fade, not a new control type.

Use a scoped draw-context opacity multiplier: child effective opacity is parent opacity multiplied by local opacity; restore the previous value on scope exit. Apply it to plain `texture` as well as tinted textures, fonts, and custom decorations. Set the effective value for every affected draw, including normal draws at 1: a new GL uniform defaults to zero, so a shader-only change could blank the rest of the UI. Respect the existing blend convention and multiply existing texture/glyph alpha once. This is per-draw modulation, so overlapping children fade individually; group compositing into a new framebuffer is not required. Keep the graphite fill's 70–85% resting opacity separate from transition opacity so fully open text remains readable. Check contrast over bright station content and keep meaning readable through labels/icons as well as colour.

Keep geometry and style work bounded on the UI side too. Reuse existing cable dirty flags and vector/buffer capacity; do not rebuild all routes merely because an unrelated settings panel fades. If profiling shows route lookup/fanning dominates after retaining clipped routes, index endpoints once per geometry rebuild rather than scan all routes for every source. Avoid new blur passes, per-frame framebuffer allocation, font rasterization, or shader compilation for decorative effects. Measure frame time and audio underruns against the same baseline scene while resizing, animating, scrolling, and dragging with many sources/routes; set any numerical budget from that baseline rather than claim performance from design alone.

## Vertical text alignment

Use the existing text-frame calculation as the starting point, then inspect actual font ascent/descent, glyph bearings, and baseline placement in [Font.cpp](../JammaLib/src/graphics/Font.cpp). Centering a nominal font pixel height does not prove the visible glyphs are centered.

- Preserve the parent's requested control/content frame even when a closest available font is chosen. Review the label-height mutation in `_ResolveFont` rather than compensate with more caller-specific Y offsets.
- Make buttons, toggles, radios, dropdowns, numeric/text inputs, popup rows, headers, and HUD labels use consistent resolved vertical geometry. `GuiButton` already sets `frame.OffsetY`; adding it again would double-offset text.
- Align text-box caret and selection rendering with the label's actual baseline/frame (`GuiTextBox.cpp`, lines 352–381), instead of independent padding assumptions.
- Controls should have common text positioning, and default height / preferred size. In this way 'vertically aligning' should cascade across all GUI controls so they all look correct together.
- Replace HUD source/trigger label magic Y values with explicit one-line/two-line layout. Include ascenders, descenders, digits, and long device names in visual checks.
- Keep intended top-aligned multiline content possible. Do not globally center every standalone label or silently change layout sizing semantics.

## Implementation flow and subagents

Use a lead agent to own integration and small Luna subagents for focused code research, with exact file/line evidence. Parallel implementation agents should have explicit file ownership; `Scene.cpp`, `GuiHud.cpp`, and shared label/render code are collision hotspots.

1. **Serial design checkpoint:** confirm coordinate/visible-rectangle contracts, event ownership after reparenting, existing-setting bindings, and default panel behavior. Turn this plan into small reviewable slices. Keep future device selection and missing feature actions outside the critical path.
2. **Parallel research:** one Luna agent traces panel/HUD layout and input routing; one traces cable geometry and hit testing; one traces device/session/group/timing command ownership. Review claims against the actual code, especially “feature exists” claims based only on fields or serialization.
3. **Serial shared foundations:** fix actual viewport layout, establish the visible-rectangle contract, and agree stable command bindings, draw/input priority, and text-frame/opacity/style interfaces. Add regression coverage for shared geometry and relocated control dispatch before consumers diverge.
4. **Parallel bounded work:** after foundations settle, develop panel composition and existing-setting bindings, cable geometry, and text/style changes in independent scopes/worktrees where useful. Assign `GuiHud.cpp` to one owner or land its changes sequentially. Keep page composition ready for future app-level actions without implementing device/session lifecycle machinery as part of layout work.
5. **Serial integration:** reparent existing settings, remove demo content and standalone paths, connect all in-scope production actions, then apply/tune motion and adornment. Compile incrementally after each meaningful integration slice.
6. **Independent review:** have a reviewer check resizing/coordinates, another inspect cable interaction/route identity, and review cross-thread bindings using the existing threading-review workflow where applicable. Review audio hot paths only if changes reach them; avoid “GUI-only” assumptions when device/timing commands are involved.
7. **Visual and performance pass:** exercise actual window resizing, scrolling, focus, popups, animations, live routing, and playback. Tune palette/motion after correctness; do not let nice borders conceal broken controls.

Prefer separate focused commits for layout, cable geometry, production pages/bindings, text, and visual polish. Do not have several agents rewrite Scene simultaneously and call the merge conflict an integration strategy.

## Verification and completion criteria

Extend existing [GuiLayout_Tests.cpp](../test/JammaLib_Tests/src/gui/GuiLayout_Tests.cpp), [GuiControls_Tests.cpp](../test/JammaLib_Tests/src/gui/GuiControls_Tests.cpp), and [CableInteraction_Tests.cpp](../test/JammaLib_Tests/src/gui/CableInteraction_Tests.cpp) where appropriate. - Resize large → small → large, maximize/restore, and resize mid-animation: anchors follow actual edges, handles remain reachable, and no unsigned overflow or virtual-window drift occurs.
- Inputs: zero/one/many sources, both categories, long/unavailable device names, widths crossing the 80 px floor, scroll offsets at both extremes, and resize after scrolling. Cards remain single-row; sockets/meters/labels stay aligned.
- Triggers: empty/long lists, append/delete, smallest useful viewport, and scrolling after resize. Card height stays 100 px and Add/Delete/header/footer remain functional.
- Cables: each station edge/corner, each scroll boundary, partial visibility, both ends clipped, nested clipping, invalid projection, and camera movement. Route IDs and destinations stay unchanged; returning into view restores real endpoints. Confirm reveal/hover, loop-editor mode, drag/reconnect, cancel, stale-revision rejection, and unavailable sources still behave correctly.
- Panels: rapid toggle reversal, tab changes during editing, popup placement, focus/capture loss, hidden-page input rejection, and scene click-through protection. Defaults reset on application restart without adding persistence.
- Binding/input regressions: each relocated control reaches the same owner after tree initialization and child additions; inactive pages consume no space or input. Verify wheel/modifier clicks and release/cancel over panels in normal and loop-editor modes, plus stationary-pointer hover during motion. Check no scene selection/master/quantisation action fires through a panel.
- Existing controls: applied-state feedback, shortcut synchronization, MIDI channel limits, quantisation states, any exposed existing tap-tempo action, offset units, and remote-follow behavior. For any existing load/save/group actions exposed, verify their current behavior. Device selection needs no runtime verification in this scope because it is not being wired.
- Text/style: compare all control families at their real sizes after resource/font initialization and resizing. Check ascenders/descenders, caret/selection, clipping, and popup rows; verify opacity does not leak into subsequent draws.
- Geometry/render regressions: finite projection before integer conversion, empty rectangles, both endpoints clipped, markers excluded from socket snapping, and visible-body grabs matching the rendered curve. Exercise nested opacity and scope restoration, including ordinary controls drawn at opacity 1 after a fading panel; visual review must cover shader-backed paths that native geometry tests cannot establish.
- Performance: compare the same populated scene before/after under playback, animation, scrolling, resize, and cable drag. Record frame-time distribution and audio underruns; check idle panels do not keep invalidating layout or rebuilding geometry. Review callback-owned code if bindings touch engine behavior, and run the threading audit for any shared-state changes.

Before **every** build/native-test run, read local `.vscode/tasks.json` and follow [build.md](build.md). Use incremental builds of affected projects and the relevant native test target; do not guess tool paths or edit machine-local tasks. Build app dependents when app wiring/resources change. No build was necessary for this planning-only document.

The feature is complete when the demo is gone, both settings panels behave correctly, the relocated settings retain their real actions, HUD geometry follows the window, cable continuations survive clipping, and text/palette/motion pass visual review during audio playback. The page structure accommodates future controls; audio/MIDI device selection and any missing feature bindings remain explicit follow-ups, with no fake working controls added.
