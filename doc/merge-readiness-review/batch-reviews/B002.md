## Checks and evidence

### Shared predicate, conversion, and egress audit

- `NinjamTiming.h:39-50` adds `IsValidNinjamTempo(float, int64_t, ...) noexcept`. It rejects non-finite BPM, values below/above the inclusive BPM bounds, and signed BPI below/above the inclusive BPI bounds. The signed input prevents a negative request BPI from becoming a large unsigned value before validation.
- `IsValidRemoteTiming` delegates BPM/BPI policy to that predicate while retaining independent nonzero interval-length and source-rate requirements. Both live timing and periodic snapshot production already call `IsValidRemoteTiming` with `constants::MinPlausibleNinjamBpm=20`, `MaxPlausibleNinjamBpm=400`, `MinPlausibleNinjamBpi=1`, and `MaxPlausibleNinjamBpi=32`, so their prior shared validity behavior remains aligned with egress.
- `IntervalSampsFromTempo` now invokes the same predicate before its first floating-point multiplication/division or unsigned conversion. It returns zero for rejected BPM/BPI and zero sample rate, preserves inclusive valid endpoints, performs arithmetic in `double`, and retains the existing saturating `unsigned int` upper bound.
- `NinjamConnection::RequestServerTempo` invokes the constants-backed predicate as its first operation. Rejection returns `false` before `FormatTempoBpm`, `std::to_string`, command-string construction, `_connectionMutex`, all four `ChatMessage_Send` calls, the success log, and the `true` return.
- Repository call-path search found one programmatic tempo-request chain: `NinjamNetworkService::SendTempoRequest` -> `NinjamSession::RequestServerTempo` -> `NinjamConnection::RequestServerTempo`. The Connection method contains the only four programmatic `/bpm`, `/bpi`, `!vote bpm`, and `!vote bpi` sends. Generic user chat remains a distinct retained API/UI behavior outside B002 and was not changed.
- The conversion helper has one production call in `NinjamNetworkService` for a valid remote snapshot's visual interval derivation. The new guard is before conversion there as well. Neither rejection path constructs or publishes timing authority.
- Static inspection therefore supports the implementation claim that invalid programmatic timing cannot reach conversion or tempo-command egress. It does not make P12 a dynamic no-egress test.

### Valid endpoints, prohibited collateral, and real-time relevance

- P12 checks inclusive `(20 BPM, 1 BPI)` and `(400 BPM, 32 BPI)` acceptance and rejects NaN, positive/negative infinity, zero, negative, just-outside BPM values, extreme finite BPM values, BPI zero, BPI 33, and maximum unsigned BPI at the `IsValidRemoteTiming` layer.
- The existing plausible-timing test also accepts the same endpoints. The existing formatting test preserves useful fractional BPM text. Static inspection shows the request boundary uses the same inclusive constants, but no test executes valid endpoint behavior through `RequestServerTempo`.
- The implementation adds no class, state machine, persisted state, connection lifecycle behavior, UI behavior, or upstream NJClient edit. It does not touch HUD, VST, window/tooling, MIDI/resources, JSON/persistence, generated assets, F-020, F-045, F-049, or F-050.
- Protected timing concepts and invariants are unaffected: the change neither maps elapsed time nor moves/rebases cursors, anchors, MIDI event positions, automation origins, policies, epochs, BPI authority, or `NoSync` state.
- The modified production call sites are network/integration paths, not the audio callback. `IsValidNinjamTempo` is `noexcept` and allocation-free. No callback allocation, exception, lock, wait, I/O, formatting, or destruction is introduced.

## Findings

### High - P12's name and the F-032 evidence claim behavior it does not test

`NinjamTimingInput.RejectsNonFiniteTempoWithoutEgress` contains only calls to `IsValidRemoteTiming`. It never calls `IntervalSampsFromTempo`, `NinjamConnection::RequestServerTempo`, or an observable existing-owner command/send boundary. Consequently:

1. Removing the new guard from `IntervalSampsFromTempo` would not fail P12.
2. Removing the new first-statement guard from `RequestServerTempo` would not fail P12.
3. P12 observes neither the request's `false` result nor a zero-send outcome.
4. The invalid table does not prove the finding's required helper-zero behavior for NaN, infinities, just-outside values, or extreme finite values.

This conflicts with the approved prerequisite name and with F-032's explicit verification contract: helper returns zero, outgoing request returns false and sends nothing, and valid formatting remains stable. `cleanup-backlog.md`, `findings.md`, and `verification-matrix.md` acknowledge that dynamic send counting is absent, but still describe P12 as the required no-egress prerequisite and mark the batch implemented/verified. Static call-chain inspection supports the current implementation, yet it cannot replace the required executable regression evidence or make the test name truthful. Correct only the named one-test prerequisite within B002; do not introduce a generic validation class/state machine or edit NJClient.

### Medium - no durable evidence proves the prerequisite passed before production movement

The prerequisite and production work are correctly separated into commits four minutes apart, but the owning verification ledger records only a build/test at `e0d60f2d` timestamped 2026-08-31T23:37:57-06:00, after the production commit at 23:37:44. It contains no command, timestamp, exit code, or counts from `c9bec2fa` before production movement. The independent review reran the current test at `ed531070`; it did not switch the shared worktree to the prerequisite commit and cannot reconstruct an unrecorded historical pass.

The prerequisite test uses only pre-existing `IsValidRemoteTiming` behavior, so it is plausible that it would have passed at `c9bec2fa`, but plausibility is not the required durable proof. On remediation, record the corrected named P12 in its prerequisite commit, prove it passes before the production correction, and retain exact wrapper command, filter, commit, timestamp, exit code, and pass/fail/skip counts.
