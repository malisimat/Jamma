# MIDI grid pointer gestures: velocity, snapped move, and pitch view

## Status and scope

Implemented on 2026-10-03. Right-drag note velocity adjustment, Ctrl + left-drag snapped note movement, and Ctrl + left-drag pitch-view control are integrated in the loop grid editor. See the implementation and verification record below for evidence and remaining manual checks. Right drag and snapped move each edit one displayed MIDI note and commit once on release through the existing MIDI edit and undo path. Ctrl + left drag from empty grid space changes only the visible pitch range. Audio loops remain view-only. The editor now has `MidiGridTargets` for note-first displayed hit testing and `LoopGridEditor` for input ownership; use those paths instead of adding a parallel picker.

## Interaction contract

- Plain left click/drag retains the editor's note add/remove paint and free-timing edit behavior. Right press on a displayed note starts velocity adjustment in both quantised and free timing views. Right press on empty editor space retains the current camera orbit behavior; it must not edit MIDI. Ctrl + right press follows the right-button velocity rule. Ctrl + left press on a displayed note requests snapped move; Ctrl + left press on empty grid space starts pitch-view control. Determine the gesture at press and keep it latched until its owning button is released or capture is cancelled.
- Resolve the visible note at press, then latch its exact source NoteOn identity and starting velocity for the whole gesture. Define deterministic precedence for overlapping displayed notes. If the displayed note cannot be mapped to exactly one source NoteOn, reject the gesture with feedback rather than change another note. Do not retarget when the pointer crosses another note or leaves the grid.
- Upward physical mouse movement raises velocity; downward movement lowers it. Use accumulated signed vertical deltas, a modest initial movement threshold, and a documented pixels-per-velocity scale. Clamp to 1–127. Ignore horizontal movement. A click or drag that returns to its initial value is a no-op. Button ownership is latched at press; another button or modifier cannot switch modes mid-drag. Right-button release completes this gesture.
- Keep the cursor anchored at the press location during an active velocity gesture when the window can safely do so. Leave the visible pointer at that anchor on completion; do not jump it to the last physical movement. Keep the captured note as the logical hover/selection target. Resume ordinary hover from the actual pointer location after release or cancellation.
- Show a live velocity number near the anchored pointer or in the editor HUD. Give **only the captured note** a clearly visible held state while the button is down. Recent commits already make the selected event white on top with a dark outline in `midi_note.frag`, and draw held paint spans in warm orange/yellow in `midi_grid.frag`. Reuse the selected note's existing edge calculation and change its outline/accent to a restrained warm held color; do not stack a second outline or cover the velocity-sensitive body with an opaque overlay. Its body color and height should preview the proposed velocity. Clear the held effect immediately on commit, rejection, cancellation, focus loss, or target invalidation. Check low and high velocities and overlapping notes for legibility.
- Update a detached edit during motion and publish one accepted raw-source edit on release. Preserve note time, pitch, channel, NoteOff, non-note events, quantisation settings, and other notes. Existing undo/redo and save/export should observe the accepted velocity. Escape, lost capture/focus, closing the editor, loop replacement, revision/grid change, or failed pointer mode cancels without publication.

## Ctrl + left drag: snapped move on a note, pitch view on empty grid

- Ctrl + left press on an unambiguous displayed note starts a **snapped move** when a MIDI time grid is resolved. Use `MidiGridTargets` to capture its source NoteOn/NoteOff identity and displayed span. The target stays fixed even if the pointer passes over other notes. A Ctrl + left click without effective cell/pitch movement is a no-op; releasing Ctrl midway does not change modes.
- During snapped move, let the actual pointer travel across the grid so its time cell and pitch row are visible. Do not warp the pointer for this gesture. Preserve the grabbed cell's offset from the note onset, then move the displayed onset to the corresponding target cell boundary and move pitch by whole semitone rows. Preserve note duration, channel, velocity, flags, and non-note events. Clamp pitch to 0–127. At loop edges, use the nearest legal grid boundary that keeps the whole note in the loop; do not silently wrap or trim it. Validate the raw-source transform by reapplying the resolved quantisation: the displayed onset and span must match the preview. Reject atomically if an inverse mapping, pairing, overlap, or boundary cannot be represented without changing another note.
- When quantisation is off or no time grid resolves, Ctrl + left on a note does not begin a snapped move; show brief feedback to enable a grid or use the existing plain-left free-timing move. Do not fall through to paint or pitch-view control. A successful snapped move uses the same `LoopTake::PublishMidiEdit` and `MidiLoopEditUndo` path as other accepted note edits, giving one undo/redo step. Escape, lost capture, changed source/grid, or editor exit discards its detached preview.
- Ctrl + left press on **empty** MIDI grid space starts a **view-only** gesture and takes precedence over plain-left paint/edit and background orbit. It never changes a note, publishes MIDI, or creates an undo entry. A Ctrl + left click without movement leaves the view unchanged. Releasing Ctrl during the drag does not switch to paint.
- Vertical physical movement pans the visible pitch range: up shows higher pitches and down shows lower pitches. This changes the model's bottom visible pitch, clamped to `0..128-visibleRows`.
- Horizontal physical movement changes how many pitch rows fit vertically: right shows more rows (zoom out), left shows fewer (zoom in). Begin with the existing supported `12..128` row bounds. Use independent accumulated X/Y deltas with documented pixels-per-row sensitivity, so diagonal dragging can pan and zoom together. Keep the pitch under the anchored pointer approximately stable when zooming alone, then apply the vertical pan delta; clamp at the MIDI limits.
- Keep the cursor anchored during the **empty-space pitch-view** gesture using the same relative-pointer mode as velocity drag. Suppress normal note hover retargeting while it is held; recompute hover after release. Existing wheel pitch scroll and Shift + wheel zoom may remain as alternate controls. If relative mode fails or focus/capture is lost, end the view gesture cleanly at its last valid view; no MIDI edit is pending.

## Relative pointer and cursor warp

`graphics::Window` already receives Win32 `WM_MOUSEMOVE`, maintains button capture, and cancels capture on focus loss. Add a small window-owned relative-pointer mode that emits movement deltas and owns cursor anchoring. `LoopGridEditor` should request/end that mode through a narrow host interface for right-drag velocity and Ctrl + left drag from empty grid space; MIDI gesture code should consume deltas without calling Win32 APIs. Ctrl + left snapped move keeps normal absolute pointer movement. Keep the relative-pointer boundary usable for future scratching.

1. Enter only after a valid right-button note press or Ctrl + left press on **empty** MIDI grid space and successful mouse capture, while the pointer is inside the client area. Record which button owns the mode. Save the anchor in client and screen coordinates using the standard Win32 conversion APIs. Do not use global hooks, synthetic `SendInput`, cursor clipping, or forced desktop switching.
2. Use `SetCursorPos` to return the cursor to the anchor after user movement. Suppress the resulting recenter notification from gesture deltas, hover, and picking. Keep normal absolute pointer handling outside this mode. A simple `WM_MOUSEMOVE` implementation needs explicit handling of coalesced/stale messages; evaluate foreground `WM_INPUT` relative movement if that cannot be made reliable, particularly before reusing the mode for scratching. Do not register for background input merely to support this gesture.
3. Keep the last valid delta/anchor state in the window adapter; derive velocity and view changes from accumulated deltas, never from the warped absolute cursor position. Treat warp failure as cancellation. Centralize teardown so the owning button's release, Escape, `WM_CAPTURECHANGED`, `WM_KILLFOCUS`, editor exit, window destruction, and scene replacement cannot leave relative mode active. Avoid repeated teardown that releases another owner's capture.
4. Reconcile window pixels, screen coordinates, resize, DPI changes, multiple monitors, and negative virtual-desktop coordinates. If the anchor is no longer within the usable client area or the window loses foreground ownership, cancel instead of warping across applications. Do not alter OS pointer acceleration settings.

Windows documents `SetCursorPos` as a supported screen-coordinate API and advises moving the cursor only while it is in the window client area: [SetCursorPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setcursorpos). Its [Raw Input guidance](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/taking-advantage-of-high-dpi-mouse-movement) distinguishes relative device movement from `WM_MOUSEMOVE` pointer coordinates. These APIs belong in the existing Win32 window layer; the editor's gesture and edit operation should remain platform-neutral.

## Code changes to plan

1. **Targets and transforms.** Extend `midi::MidiGridGesture` or add narrow companion transactions for velocity and snapped move. Resolve note identity through the existing `MidiGridTargets::Build/Resolve` path, which preserves source indices through quantised display and identifies ambiguous pairing. Keep plain-left paint and free-timing move unchanged. Add a pure `MidiEditOperations` velocity operation that changes only the captured NoteOn's `data2`; do not re-sort for that edit. For snapped move, use or carefully extend `MoveOrTrim` on a detached revision, validate the quantised result, and preserve event metadata and duration. Avoid making the existing raw free-move path the sole authority for a quantised displayed target.
2. **Input ownership and pitch view.** In `LoopGridEditor`, route right-on-note to velocity, Ctrl + left-on-note to snapped move, and Ctrl + left-on-empty-grid to pitch view before the current left paint/background orbit and right orbit branches. Latch button and gesture kind. Use relative deltas and cursor anchoring only for velocity and pitch view; use `_PointAt` and the moving pointer for snapped move. Accepted note edits commit through the existing `_PublishGesture`/`LoopTake::PublishMidiEdit` undo path; pitch-view release only ends pointer ownership. Use `MidiModel::SetEditorPitchRange` for pan and zoom and keep the starting view/anchor pitch for stable delta mapping. Decide a narrow Window–editor host request/result interface so Window does not depend on MIDI types and the editor does not manage Win32 cursor state. Suppress paint, orbit, HUD activation, and unrelated hover changes while a gesture owns its button.
3. **Visual state.** `MidiModel::SetEditorTarget` and `EditorTargetInstance` already identify one note instance for the current white-top/dark-outline selected state. Verify this instance matches the captured `MidiGridTargets` note after quantisation, model refresh, and seam-copy rendering. Add a transient held gesture mode and proposed velocity for the captured instance; reuse the existing edge/outline calculation in `midi_note.frag`, changing the held edge to a warm accent consistent with `midi_grid.frag` while preserving the velocity palette on the body. For snapped move, show the original note as held and a clear target ghost at the proposed displayed cell/pitch; ensure any paint preview geometry does not obscure the note. Keep the ring endpoint, picker pass, ordinary hover, playhead, and grid seam copies intact. Avoid rebuilding all note instances on every pointer move or publishing source events during preview.
4. **Feedback and lifecycle.** Display proposed velocity, snapped destination, or visible pitch range as appropriate, plus clear ambiguous-target, unrepresentable-move, and warp-failure feedback. On every exit path clear the held shader state, target ghost, preview value, pointer mode, and ownership together. If a model update changes instance order or the source revision/grid changes during a note edit, cancel rather than let the visual target drift to another note. A pitch-view drag must not depend on a source revision.

## Acceptance criteria

- Plain left click/drag retains note add/remove behavior. Right dragging one visible note adjusts only its velocity, including in quantised view, and produces one undoable edit on right release. Right drag on empty space retains camera orbit. A click without effective movement produces no edit.
- Ctrl + left drag on a note with a resolved grid moves the whole note by grid cells and pitch rows, previews its destination, and produces one undoable edit. Ctrl + left drag on empty grid space pans visible pitches vertically and changes the visible row count horizontally, with no MIDI or undo change. Releasing Ctrl mid-drag does not change the gesture.
- The cursor stays at the press anchor during right drag or Ctrl + left **view** drag when relative mode is active; it follows the grid during Ctrl + left **note move**. Dragging across other notes does not retarget the captured note. Pointer behavior is normal immediately afterward.
- The held note alone has a warm variation of the existing outline, and its previewed color/height and displayed number track the proposed velocity. Snapped move has a distinct destination ghost. All effects clear on every exit path.
- Ambiguous source mapping, failed warp, stale state, and cancellation leave source MIDI and undo history unchanged. Window capture and cursor state cannot remain stuck.

## Implementation and verification record (2026-10-03)

Research was separated into input/window, MIDI identity/edit, and graphics/UX subagent phases. Those agents then implemented disjoint files; the main agent integrated input ownership and publication, added editor-level tests, and reviewed the complete change.

- `MidiGridGesture` captures one source identity through `MidiGridTargets`; velocity writes only NoteOn `data2`, and snapped movement preserves raw duration and explicit endpoint metadata. Accepted edits publish once through the existing take/undo path.
- `MidiPitchViewGesture` accumulates independent pan/zoom deltas and maintains the fractional pitch anchor. The view gesture has no MIDI transaction or undo entry.
- `Window` owns foreground `WM_INPUT`, capture validation, anchoring, raw-registration restoration, and lifecycle teardown. All absolute recenter/stale mouse messages are excluded during relative mode. Relative sensitivities use device movement units, not screen pixels: velocity uses a 3-unit threshold and 4 units/value; pitch pan uses 12 units/row and zoom uses 8 units/row. Device DPI therefore affects feel; OS pointer acceleration remains untouched.
- The captured note alone receives a warm version of the existing edge, with uniform velocity body/height preview. Its depth bias keeps low-velocity captures visible over higher overlapping notes. Snapped destinations use a translucent cyan ghost. Applied model replacement clears transient state and invalidates the gesture. Press-time metadata checks reject a display that is behind the current source.
- Incremental Debug builds succeeded for JammaLib, Jamma, and JammaLib_Tests using local task commands. The complete native suite passed 1,099 tests; one hardware-dependent MIDI-device test skipped. Focused final-review tests cover stale displayed instances, no-op velocity, grid-disabled Ctrl press, and model/resize cancellation. The audio hot-path audit passed; callback bodies have no changes.
- Both note/grid shader pairs compiled and linked on the local OpenGL 4.6 NVIDIA driver. An isolated render of the actual note shaders at velocities 1, 64, and 127 was visually inspected: body palette remains visible beneath one warm edge. This is shader evidence, not an interactive app screenshot.

New gesture, host, applied-display metadata, generation, and held-preview fields are UI/render-owned. The job-side model metadata travels inside the existing immutable pending model snapshot and is applied via its existing atomic handoff. No new audio-thread shared state, lock, or publication mechanism was added. Scene/window teardown cancels the editor before detaching callbacks or releasing resources.

Remaining manual verification: real mouse fast movement and sensitivity on multiple device DPIs; Alt+Tab/Escape and release outside the client area; negative-coordinate monitors and display scaling; VST/plugin raw-input registration interactions; in-app low/high velocity overlaps, seam copies, narrow rows, and destination ghost legibility. Strict endpoint preservation intentionally rejects seam moves requiring a NoteOff to be created or removed; rejection leaves source and undo unchanged. Absolute-device/tablet input cancels relative mode cleanly. These limitations do not broaden audio-thread scope.
