# Jamma self-validation

Use this skill from the active Jamma checkout on Windows. Verify its root with `git rev-parse --show-toplevel`, `Jamma.sln` and `AGENTS.md`; locate every script relative to this `SKILL.md`, never from another checkout. Read `doc/diagnostics.md`. Require the successful JSON build record from the active worktree's task wrapper, then run `scripts/resolve-jamma-build.ps1` to check `Jamma/bin/x64/<Configuration>/Jamma.exe`, task-file hash and binary hash. No script contains a user-specific path. Never use Start menu, PATH, an installed copy or the main checkout for worktree validation.

Before launch, inspect all Jamma processes and stop the runtime check if another instance may hold unsaved work. Use `scripts/launch-test-session.ps1` only with the validated record and a fresh disposable `defaults.json` path in the ignored run directory. It sets `JAMMA_DEFAULTS_PATH` only for that process and returns PID, path and start time. Confirm the running process executable path matches the exact build before interacting.

Use the official `computer-use` skill first. Select the exact returned Jamma window, exercise the stated scenario, and inspect the rendered UI for clipping, dialogs and behavior. Request a screenshot-backed observation and pass its saved path to `capture-window.ps1` for PID, window, timestamp and hash checks. A screenshot proves one frame, so report interaction evidence separately.

If official screenshot capture reports `FrameArrived`, `window capture`, or `timed out waiting on channel`, do not retry indefinitely. Follow the computer-use recovery rule: refresh the target once, reset the computer-use session once, and retry once. If the same capture failure remains while accessibility/window discovery works, classify the official capture backend as unavailable and use the scoped fallback below. Do not alter Windows privacy/security settings, patch the global Computer Use plugin, or substitute a screenshot from another process.

Fallback route: run `scripts/capture-window-fallback.py` with the validated session PID and a fresh output path. It enumerates visible windows, requires exactly one visible `Jamma` window owned by that PID, captures only that window through the standard Win32 `PrintWindow` API (with a bounded `BitBlt` fallback), and writes a PNG without user-specific paths. Inspect the resulting image directly; reject black, inverted, clipped or stale output. Then pass that PNG through `capture-window.ps1` and `inspect-runtime.ps1` exactly as with official evidence. Record `capture_method=win32-printwindow-fallback` and the original official error in the evidence/run report. This is a fallback screenshot, not proof that official Computer Use recovered. If `pywin32` is unavailable or the window cannot be enumerated, report the fallback as unavailable rather than installing arbitrary packages or claiming visual validation.

Use `collect-logs.ps1` with the session start time and explicit defaults path to collect timestamp-bounded startup and worker-failure logs. `inspect-runtime.ps1` checks the saved evidence manifests and hashes; the agent must still inspect behavior and log content. Record successes and concrete failures. Close only the disposable Jamma session you launched, without disturbing another process. Prefer orderly UI close; if the app intercepts it or coordinate input is unavailable, recheck that the PID still maps to the exact validated binary and terminate only that disposable PID, recording orderly shutdown as unverified. If both official and fallback capture are unavailable, say so; do not substitute an older binary. Real ASIO, MIDI/serial hardware, plugin sound, timing and subjective UX remain manual gates when no reliable probe exists. Do not disturb a live performance or add callback logging.

For cross-thread/audio changes, invoke the checkout's `threading-review`; for texture work use `tga-icon-gen`. Resolve repo-local skills from this checkout.
