## Findings

### High — the connection-use acquisition and unpublish protocol has an unclosed entry race

`NinjamSession::_AcquireConnectionUse()` first loads `_connection` at `NinjamSession.cpp:366`, then increments `_activeConnectionUsers` at `:370`, then validates `_connection` with another acquire load at `:371`. Concurrently, `_UnpublishConnectionLocked()` exchanges `_connection` to null at `:352`, observes `_activeConnectionUsers` at `:356`, and transfers `_ownedConnection` at `:359`.

The two atomics use acquire/release operations but have no single total ordering or entry gate. A permitted execution is:

1. The callback's first `_connection` load obtains the published pointer.
2. `Stop()` exchanges `_connection` to null, observes the user count as zero, and transfers ownership without waiting.
3. The callback increments the user count. Its validation load is not required by acquire/release ordering to observe the concurrent null exchange and may still observe the earlier published value, so it returns the pointer as a successful guard.
4. `Stop()` disconnects and can destroy the connection without another user-count wait while `AudioHost.cpp:435` dereferences that pointer or consumes its scratch storage through `:438`.

Thus the new call site has the desired lexical scope but not a guaranteed lifetime pin. This is the same use-after-free class B001/F-033 is required to close, and fixing the existing scoped-use implementation is explicitly inside B001's `NinjamSession.h/.cpp` ownership boundary. The correction must preserve the callback prohibition on locks, waits, allocation, I/O, formatting, and final destruction.

P9 does not detect this race: it completes `NinjamConnectionUse connectionUse(session)` at test line 26 before creating the stop thread at lines 29–33. Its later acquisition loop begins only after the original guard already makes the active count nonzero, so `Stop()` cannot take the zero-user path involved above. Add or correct only the named P9 prerequisite to force acquire/unpublish entry overlap and prove that every successfully returned use was included in retirement; do not add a raw-buffer test API.

### C++ memory-model and lifetime proof

For a reader, the sequentially consistent operations are count increment `C`, then pointer load `L`; program order requires `C < L` in the single sequentially consistent order. Retirement performs null exchange `X`, then one or more count loads `W`, so `X < W`.

- If `L` returns the published pointer, `L` must precede the retiring `X`; otherwise the sequentially consistent load would observe the null exchange. Therefore `C < L < X < W`. The count contains this reader at every retirement observation until the guard's release `D`, which occurs only after the guarded operation and synchronous ingestion return. Retirement cannot observe zero and transfer `_ownedConnection` before `D`.
- If retirement wins, `X < C < L`; absent a later publication, `L` observes null and the reader immediately decrements without dereferencing the connection. Publication and unpublication are serialized by `_lifecycleMutex`, and retirement holds that mutex through its zero-count observation, so a replacement publication cannot create an ABA window inside this proof.
- The successful reader's sequentially consistent decrement releases all preceding guarded connection/scratch-buffer accesses, and the retiring sequentially consistent zero load acquires that completion before ownership transfer. `Disconnect()` and destruction occur after the lifecycle critical section on the Stop/Start caller, never in `NinjamConnectionUse` destruction.

The former rejected execution is consequently impossible: retirement cannot be ordered between a pointer load and a later count increment because the corrected reader increments before loading. Unlike the rejected retry loop, callback admission now executes a fixed count increment and pointer load, with one immediate decrement only on the null path; successful guard destruction executes one decrement. There is no callback-side mutex, condition variable, yield, software retry, allocation, exception, I/O, formatting, dynamic copy, or connection destruction. On the approved Windows x64/MSVC target these integral/pointer atomics are implemented lock-free; the callback's own protocol has a bounded instruction sequence and does not wait for retirement. The only polling loop remains in `_UnpublishConnectionLocked()` on the non-callback lifecycle caller.

`AudioHost.cpp` constructs the guard before `ConsumeStereoPair` and retains it through `StationRemote::IngestStereoBlock`. That ingestion synchronously copies through both `OnBlockWriteChannel` calls and both `LoopRemote::IngestSamples` calls before returning; it does not retain either scratch pointer. Guard destruction follows the complete ingestion call. The Session/Controller wrappers that previously returned scratch pointers after destroying their local guard remain removed.
