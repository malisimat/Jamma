## System understanding

There are currently three related state machines with no single aggregate authority state:

1. **Physical connection:** `NinjamConnection::ConnectionState` is `Disconnected`, `Connecting`, `Connected`, `Retrying`, or `Failed` (`NinjamConnection.h:66`–`:73`). `Pump` drives NJClient and auto-retry (`NinjamConnection.cpp:299`–`:404`). `NinjamSession::Pump` returns a snapshot only while `IsConnected()` is true (`NinjamSession.cpp:452`–`:463`).
2. **Timing/session intent:** `Scene::ConnectNinjam` calls coordinator `Connect`, clears the prompt, and publishes audio invalidation before it starts/replaces the physical session (`Scene.cpp:254`–`:287`). Explicit `DisconnectNinjam` resets coordinator state, closes the prompt, publishes invalidation, then stops the physical connection (`Scene.cpp:290`–`:310`). `NinjamTimingTracker::_connected` therefore represents requested timing-session intent, not observed network availability.
3. **Accepted audio authority:** coordinator updates are materialized by Scene and published to AudioHost (`Scene.cpp:403`–`:482`). AudioHost owns active follow policy/map and consumes one command at a block boundary (`AudioHost.cpp:162`–`:330`). There is a diagnostic receipt (`AudioHost.cpp:113`–`:133`, `:321`–`:329`), but production never feeds application acknowledgement back into the coordinator; `NotifyPhaseCorrectionConsumed` is used only by the test harness (`NinjamTimingCoordinator.h:163`; `NinjamTimingIntegration_Tests.cpp:162`).

The request sub-state is `Idle`, `Queued`, `SentAwaitingOutcome`, `Acknowledged`, or `Expired` (`NinjamTimingCoordinator.h:33`–`:43`). A request begins queued on coordinator connect, is sent at a remote wrap, and can retry or expire only while valid observations produce wrap events (`NinjamTimingCoordinator.cpp:10`–`:29`, `:178`–`:214`). A wall-clock deadline exists but is evaluated only inside `Observe` after the connected/valid/interval guard (`:68`–`:97`). Prompt state is split between coordinator `_pendingTempoChange` and Scene/UI `_remoteTempoDialogOpen`; Scene reconciles changed proposals on snapshots and opens/closes the popup during UI commit (`Scene.cpp:336`–`:400`, `:1667`–`:1704`).

This separation is workable only if every availability edge is propagated. Explicit user disconnect does so. Unexpected connection loss, retry, authentication failure, or an invalid timing stream does not: `NinjamSession::Pump` collapses every non-connected state to `nullopt`, and `Scene::OnJobTick` simply does nothing when no snapshot exists (`NinjamSession.cpp:452`–`:463`; `Scene.cpp:1382`–`:1396`). That leaves coordinator, prompt, remote-station presentation, and AudioHost authority in states belonging to the prior connection.

## Candidate findings

### S10-01 — Propagate physical connection loss and auto-reconnect as timing-session epoch transitions

- **Stage / reviewer:** Stage 10 — state machine and failure paths.
- **Scope reviewed / exclusions:** unexpected availability changes and recovery ownership. Command delivery and per-take generation bugs are S09-01/S09-02; connection object lifetime is Stage 12.
- **Severity:** merge blocker.
- **Evidence:** `NinjamConnection::Pump` transitions the physical state among `Connecting`, `Connected`, `Retrying`, and `Failed` at `JammaLib/src/ninjam/NinjamConnection.cpp:299`–`:404`. On loss it sets `_isConnected=false` and schedules retry or failure (`:374`–`:400`). `NinjamSession::Pump` hides every non-connected state by returning `std::nullopt` (`JammaLib/src/ninjam/NinjamSession.cpp:452`–`:463`). `Scene::OnJobTick` only handles timing/session state when a snapshot exists and otherwise performs no invalidation, prompt closure, coordinator disconnect, or remote-station cleanup (`JammaLib/src/engine/Scene.cpp:1382`–`:1396`). Only explicit UI `DisconnectNinjam` performs those transitions (`Scene.cpp:290`–`:310`). On internal retry success the same connection resumes snapshots without calling `NinjamTimingCoordinator::Connect`, so tracker `_connected`, `_generation`, `_joinPending`, request/prompt state, and command generation retain the prior physical session (`NinjamTimingCoordinator.cpp:10`–`:47`; `NinjamTimingTracker.cpp:5`–`:26`). Remote stations are removed only by a later connected snapshot's user set (`NinjamNetworkService.cpp:47`–`:143`). History shows the snapshot-null contract predates the timing coordinator (`NinjamSession.cpp:452`–`:463`), while coordinator/session invalidation was added in `f36bfe7`/`d6fdb88` and retry behavior remains inside the older connection pump.
- **Why it matters:** During a network outage the system can simultaneously be physical `Retrying` or `Failed`, coordinator “connected,” request `SentAwaitingOutcome`, prompt pending/open, remote stations marked connected, and AudioHost still following the old map. Auto-reconnect is then not an independent follow session: stale joins/wraps/commands can cross the outage, and fresh anchors/session generation are not guaranteed. This violates the documented rule that disconnect/`NoSync` clears map and anchors and that the next session captures a new origin.
- **Recommended disposition:** make connection availability/epoch an explicit value emitted by the connection/session owner and consumed once by the NINJAM integration owner. On `Connected -> Retrying/Failed/Disconnected`, close/cancel prompt and request state, publish one complete `NoSync` invalidation, mark remote stations unavailable, and remember that no remote authority is active. On retry success, start a fresh coordinator/tracker session epoch and require new valid timing before authority is accepted. Keep physical retry policy in `NinjamConnection`; do not make Scene infer state from missing snapshots or create another timing implementation. Reconcile with S09-01/S09-02 so the loss transition cannot be dropped and every audio consumer resets the same epoch.
- **Protected timing concepts affected:** connection availability, remote session epoch, follow policy, `NoSync`, map/scene-anchor lifecycle, command generation, and per-entity phase remain distinct.
- **Verification:** a production-faithful fake connection/state source should drive `Connected -> Retrying -> Connected`, `Connected -> Failed`, authentication failure, explicit disconnect during retry, and repeated loss notifications. Assert exactly one invalidation per loss edge; local Timer/loops free-run during outage; prompt/request/remote stations clear; retry success requires a fresh valid observation and new anchors; stale prior-session commands are rejected; unequal loop lengths/offsets survive. No current native test covers `NinjamConnection::ConnectionState` transitions.
- **Human decision:** pending.

### S10-02 — Give invalid or absent timing an explicit recovery transition and an observation-independent deadline tick

- **Stage / reviewer:** Stage 10 — state machine and failure paths.
- **Scope reviewed / exclusions:** malformed/late/unavailable input and timeout progress. Validation thresholds/formulas belong to Stage 11; NJClient publication race is S07-01.
- **Severity:** must fix before merge.
- **Evidence:** `NinjamTimingCoordinator::Observe` immediately returns an empty update when timing is disconnected, invalid, or has zero interval (`JammaLib/src/ninjam/NinjamTimingCoordinator.cpp:68`–`:77`, introduced in `f36bfe7`). This guard precedes the wall-clock request deadline at `:81`–`:97`, so a successfully sent request never reaches `Expired` if observations stop or stay invalid. Wrap-count retry/expiry also requires valid tracker events at `:178`–`:214`. More importantly, an active accepted follow session receives no `InvalidatePendingCorrections`/`NoSync` transition when a connected stream becomes implausible; AudioHost therefore retains prior `_activeNinjamFollowPolicy` and `_syncPhaseMap` (`JammaLib/src/audio/AudioHost.cpp:174`–`:186`, `:456`–`:459`). Existing deadline/retry tests provide continuing valid observations (`test/JammaLib_Tests/src/ninjam/NinjamTimingCoordinator_Tests.cpp:490`–`:546`); the disconnect test calls `coordinator.Disconnect()` explicitly (`:229`–`:240`) rather than presenting invalid/absent timing.
- **Why it matters:** “invalid” currently means “silently preserve the previous state,” not “remote timing is no longer authoritative.” A transient invalid value before handshake should merely wait, but invalidity after accepted authority must fail closed and recover. Request deadlines also promise time-based recovery yet can remain `SentAwaitingOutcome` indefinitely when the observation source fails—the exact condition a deadline is meant to handle.
- **Recommended disposition:** let the coordinator/integration owner receive an explicit periodic availability/timing-validity tick even when no valid timing sample exists. Track whether remote authority was ever active. Before first authority, invalid input remains a bounded waiting state; after authority, the first invalid/unavailable edge emits one complete `NoSync` invalidation and clears prompt/request state as policy specifies. Evaluate wall-clock request deadlines from the job tick, not only from valid observation handling. A later valid stream should enter through a fresh generation/epoch transition, not silently continue the old map. Coordinate with S10-01 so physical absence and malformed connected timing share one recovery contract without duplicate invalidations.
- **Protected timing concepts affected:** timing validity, remote authority, request deadline, follow policy, `NoSync`, generation, and map/anchor invalidation remain separate.
- **Verification:** tests for invalid-before-first-authority (no movement/no spurious repeated invalidation), valid accepted authority followed by invalid/zero/disconnected observations (one invalidation and free-run), invalid stream through and beyond request deadline (request expires without another valid sample), recovery to valid timing (fresh generation/anchors), and repeated invalid samples (idempotent). Include prompt-open and request-awaiting variants.
- **Human decision:** pending.

## Uncertainties

- `NinjamConnection::Pump` has no injectable clock/client in production, and there are no native tests for its `ConnectionState` transitions. The exact fixture seam is an implementation decision; the missing propagation follows directly from `Session::Pump -> nullopt` and Scene's `if (snapshot)` control flow.
- A short invalid timing observation is expected during NINJAM handshake. The correct grace/debounce rule is a human/product decision only if immediate post-authority invalidation would be too aggressive. The state machine must nevertheless distinguish pre-authority waiting from loss after accepted authority and document any bounded grace period.
- It is unclear whether remote stations should be immediately removed or retained visually as disconnected during auto-retry. They must not remain marked connected and feed active authority. Product presentation can vary without changing the timing invalidation requirement.
- Failed tempo-request delivery intentionally returns to `Queued` without consuming the retry budget (`Coordinator.cpp:49`–`:66`). This can retry indefinitely while valid wraps continue. No separate finding is filed because the code comment makes that policy explicit; Stage 17 should make repeated delivery failure visible, and the human gate may accept or revise it.
- Audio initialization failure can leave a job/network producer with no audio command consumer. No incorrect movement was proved because no callback runs. Stage 12 should verify shutdown/retry lifetime, and Stage 16 may own user-visible startup recovery.
- Teardown ordering appears intentionally producer-before-consumer (`Scene.cpp:1639`–`:1649`; `AudioHost.cpp:94`–`:106`), but idempotent low-level destruction and active-use waits remain Stage 12.

## Conclusion

Explicit user connect, prompt accept/reject, valid request acknowledgement/retry/expiry, remote user membership changes, and explicit disconnect have recognizable owners and mostly complete state intent. Their audio application is still blocked by Stage 9's command-history and generation findings.

Stage 10 adds two evidence-backed failures: unexpected physical loss/auto-reconnect never becomes a timing-session epoch transition (S10-01, merge blocker), and invalid/absent timing neither invalidates prior authority nor permits observation-independent request deadlines to progress (S10-02, must fix before merge). Together they explain how the application can remain in mixed physical/coordinator/audio/UI states after failures. Phase 2 cannot accept transition completeness or recovery until these are reconciled with S07-01/S07-03 and S09-01/S09-02; no source cleanup is authorized by this report.
